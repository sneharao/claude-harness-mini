# Init Harness (existing project)

## When to use this skill

You ran `rsync --ignore-existing` (or equivalent) to graft this harness onto a project that already has source code. The codebase exists; you are bolting the harness on top of it.

For a **fresh** project (no source code yet), do not use this skill — run `/harness/000-design` instead.

## What you'll produce

- An audit of the existing codebase: detected domains, classified architecture shape, branch-naming compliance, coding-convention drift. Written to `harness/exec-plans/000-onboard/audit.md`.
- The three domain knowledge files, seeded from the audit and confirmed by the human.
- AGENTS.md placeholders resolved.
- Stack-specific knowledge files generated by the matching persona (if one matches the detected stack).
- A summary the human can act on: what the harness now knows, what drift needs fixing, what to do next.

This skill is **idempotent** — running it twice is safe; it will ask before overwriting.

## Steps

### Step 1 — Verify edit-capable mode

This skill writes files. If you are in read-only mode, switch before proceeding.

### Step 2 — Confirm project is existing

Check for source code:

```bash
ls -la src/ app/ 2>/dev/null
test -f package.json && echo "package.json present"
```

If the project is genuinely fresh (no source code, no `package.json`, no equivalent), stop and tell the human to run `/harness/000-design` instead. This skill is for grafting onto existing projects.

### Step 3 — Detect harness state

Check what the harness already has:

| Check | If present |
|-------|-----------|
| `harness/exec-plans/000-onboard/audit.md` | Audit already run — ask whether to re-run |
| `harness/knowledge/domain/problem-statement.md` | Domain already seeded — ask whether to re-seed |
| `AGENTS.md` contains `{{PROJECT_NAME}}` | Placeholders unresolved — needs name/tagline |

Confirm with the human before overwriting anything.

### Step 4 — Run the audit

Read and execute `harness/skills/init/audit-existing-project.md` in full. It is read-only and produces `harness/exec-plans/000-onboard/audit.md` with sections:

- **Detected stack** — language, framework, package manager.
- **Detected domains** — candidate entity nouns extracted from folder/file names.
- **Architecture shape** — vertical slices / n-tier / mixed / unclassified.
- **Branch-naming compliance** — fraction of branches matching `<type>/<short-desc>`.
- **Naming-convention drift** — sample of file/identifier names that don't match `naming-conventions.md`.

When the audit returns, read the file and present a short summary to the human.

### Step 5 — Seed domain knowledge

Read and execute `harness/skills/init/seed-domain-knowledge.md` in full. That skill reads the audit and walks the human through confirming/correcting the detected nouns and writing:

- `harness/knowledge/domain/problem-statement.md`
- `harness/knowledge/domain/entities.md`
- `harness/knowledge/domain/ubiquitous-language.md`

### Step 6 — Resolve AGENTS.md placeholders

Grep for `{{` placeholders in `AGENTS.md`:

```bash
grep -n '{{' AGENTS.md
```

For each placeholder, ask the human:

- `{{PROJECT_NAME}}` — propose the repo's directory name as a default.
- `{{PROJECT_TAGLINE}}` — propose the first sentence of an existing `README.md` if one exists.

Replace with the human's chosen values. Verify zero `{{` remain.

### Step 7 — Apply matching persona (knowledge only)

From the audit's detected stack, look for a matching persona:

```bash
ls harness/skills/init/persona-*.md
```

Read each persona's first heading to match against the detected stack. If exactly one matches, show the human:

> Detected stack: `<stack>`. Persona `persona-<stack>.md` matches. Apply its stack-specific knowledge files? (This skips its `package.json` block — the project already has one.)

If the human agrees, execute only the persona's `### Output → <path>` blocks where `<path>` starts with `harness/knowledge/` or `harness/skills/`. Skip:

- The `### Merge into package.json` block (the existing `package.json` is authoritative).
- Any output that would overwrite an existing file without confirmation.

If no persona matches, tell the human:

> No persona matches the detected stack. Stack-specific knowledge files (`typescript-and-zod.md`, framework patterns, etc.) won't be generated. You can author them by hand or add a `persona-<stack>.md` later.

### Step 8 — Present drift findings

Read the audit's compliance sections. Print to the human:

- **Branch-naming drift** — branches that don't match `<type>/<short-desc>`. Suggest renaming, do not auto-rename.
- **Naming-convention drift** — files or identifiers that don't match `naming-conventions.md`. Suggest fixes; do not auto-edit.
- **Architecture drift** (if applicable) — places where the detected shape contradicts what code in that area is doing. Suggest writing an ADR (`harness/skills/planning/write-adr.md`) to either accept the divergence or plan a migration.

These are surfaced as suggestions, not actions. The human triages them — typically by opening a normal plan via `/harness/001-plan onboard-cleanup` to address them.

### Step 9 — Commit

Stage and commit the harness onboarding output:

```bash
git add AGENTS.md harness/knowledge/domain/ harness/exec-plans/000-onboard/
git commit
```

Per `harness/skills/development/commit-changes.md`. Push if a remote is configured.

### Step 10 — Summary

Tell the human:

- What the harness now knows about the project (one-line each: stack, domains, architecture shape).
- Open drift items with severity (none / minor / blocking).
- Recommended next action — either `/harness/001-plan onboard-cleanup` if drift is significant, or `/harness/001-plan <first-task>` to start normal feature work.

## Done

The harness has been bootstrapped onto the existing project. Knowledge files reflect the project's actual state. Drift is surfaced but not auto-fixed. The human knows what to address next.
